## Reports

### Codex native Astra/xhigh — E02 and E20

The best first default-preserving candidate is small: avoid constructing and immediately discarding empty component-dirty result containers. That is worth a bounded allocation/CPU experiment. It does not eliminate diff construction or world-state walks, and no measured benefit is claimed. Broader shortcuts have concrete compatibility counterexamples; those counterexamples reject the specific shortcuts, not every possible optimization.

E02 current behavior. src/world-tick.ts:178-196 always builds a diff after systems/resources and before advancing the tick. src/world-tick.ts:300-334 collects entities, component dirtiness, resources, world state, tags and metadata. For every registered component store it calls getDirty(), then discards the returned container if both arrays are empty. ComponentStore.getDirty at src/component-store.ts:110-117 creates a set array, a removed array and an enclosing object even when both underlying dirty sets are empty. ResourceStore.getDirty already skips this empty case at src/resource-store.ts:246-250; that is a verified surrounding-code precedent.

Candidate E02 experiment. Add only an internal component-store dirtiness query or equivalent internal branch that checks dirtySet.size and removedSet.size before World builds a component dirty payload. Preserve ComponentStore.getDirty's existing result contract for direct callers. Continue visiting stores in the existing order, and preserve all nonempty paths, live payload references, structural metrics, resource/entity/tag/state processing, failure behavior and currentDiff publication. This introduces no World option, persistent field, new dependency, public policy or caller obligation. Do not combine the experiment with state-fingerprint changes, lazy diff publication or listener cloning changes; each has different correctness obligations and would obscure attribution.

Why a listener-count skip is not equivalent. World.getDiff at src/world-observers.ts:87-88 exposes the last tick's diff independently of subscriptions. PlayerObserver polls it at src/player-observer.ts:250, and WorldDebugger reads it at src/world-debugger.ts:142. Recorder, render, client and history adapters subscribe at src/session-recorder.ts:190, src/render-adapter.ts:156, src/client-adapter.ts:142 and src/history-recorder.ts:216. Headless does not mean unobserved: SessionRecorder consumes diff/events/metrics in its _onDiff path at src/session-recorder.ts:384. A world with no listeners can still be observed through getDiff after its step. Renderer absence and a zero diff-listener count therefore do not prove that no consumer needs the diff.

Why a lazy build is a separate design. Dirty membership is cleared at the next tick start (src/world-tick.ts:123-127,262-277), while diff construction currently occurs at a defined tick phase. A delayed builder would need to retain the exact membership and relevant ordering before those clears, account for subsequent live-reference mutations, and preserve when construction errors poison the world or consume a tick. Moving this work into getDiff would also relocate duration accounting and errors into an observer call. It is not just an allocation deferral. A carefully designed internal capture could be investigated, but no equivalent construction has been demonstrated here.

Why one shared serialization for all listeners is not a free substitution. The emission loop clones currentDiff separately for each listener (src/world-tick.ts:208-215). That isolates one listener's diff object from another, but currentDiff payloads still reference live state/component values. A listener can mutate a live object through a world reference before the next clone; a later listener can therefore observe the later value. Serializing once before the loop would change that behavior and the number/order of supported getter/toJSON observations. The absence of mutations to the received clone does not establish immutability of the underlying world. Likewise, getDiff clones at the time it is called; changing the internal payload to a permanently frozen tick snapshot is a contract decision.

E20 current temporal roles. At tick start, clearStateDirty clears setter/removal bookkeeping and fingerprints every stored state value (src/world-tick.ts:271-277). At diff construction, getStateDirty starts with explicitly marked keys and fingerprints only keys not already marked dirty (src/world-tick.ts:280-297). These are distinct temporal observations, not duplicate calculations of a guaranteed-identical object. A slot untouched by setters can be scanned twice; a dirty-marked slot skips the second scan. The historical AoE2 measurements in docs/engine-feedback/current.md:48 establish the consumer's reported motivation, not a refreshed measurement of this source.

Live references are an explicit present behavior. setState validates but stores the supplied value directly; getState returns that reference (src/world-observers.ts:221-235). deleteState removes the value, removes its dirty marker and adds its removal marker; a later setState adds the dirty marker and clears removal (lines244-252 and225-228). A caller can mutate the original object or getState's result between ticks or during a system. Ordinary setter calls are themselves dirty events, including equal-value writes. Optimizations must preserve delete/reinsert and setter intent, not merely compare final JSON values.

Concrete stale-baseline counterexample. Suppose the last completed tick ended with slot.v=0. Between ticks, a retained reference changes it to1; a system changes it back to0 without calling setState. The present start-of-tick baseline is1 and the end value is0, so the diff reports the change. Reusing the previous completed tick's fingerprint0 would miss it. The converse also matters: a between-tick change0→1 with no in-tick change gives baseline1/end1 and no new state.set entry under the existing algorithm; comparing only previous endpoint0/end1 would invent an in-tick diff. A persistent fingerprint cache keyed only by setters cannot distinguish these cases.

Explicit setters are not interchangeable with semantic equality. setState marks its key even if it receives the same reference or an equal value. Component stores also have separate strict/semantic rules: tests/component-store.test.ts:148 documents that raw in-place component mutation does not itself mark a component dirty, and the later semantic tests preserve equal-set behavior and generation changes. World-state in-place detection therefore cannot simply inherit the component-store incremental-baseline implementation. Preserve the existing asymmetry unless a new policy is chosen deliberately.

Supported observation effects constrain traversal fusion. jsonFingerprint calls assertJsonCompatible and then JSON.stringify (src/json.ts:67-69). The validator eagerly obtains enumerable object entries at line56, visits array elements in index order, checks prototypes/cycles, and propagates original native getter failures. Plain objects with getters can pass validation. A non-enumerable toJSON method is outside Object.entries validation but can be invoked by JSON.stringify. Freezing an object does not make an accessor pure or prevent it from closing over mutable data. A Proxy can sometimes pass the live validator while still being rejected by structuredClone at serialization, so this report does not promise general proxy serialization support. World.serialize explicitly validates and structured-clones components/state (src/world.ts:82-83,118). Existing tests/json-validation-contract.test.ts:56 and66 protect getter read order and original exception identity. Any default-preserving shortcut must preserve effects only where the existing relevant operation supports them; it must not invent a stronger JSON/Proxy/toJSON contract.

Error timing also distinguishes the scans. Tick-start state baselining occurs in the outer try/finally without the diff-phase failure conversion. An error while getStateDirty runs inside buildDiff goes through the phase 'diff' / code 'diff_build_threw' failure path at src/world-tick.ts:180-193; non-listener tick failures consume their tick at lines252-256. Moving, removing or merging traversals can therefore change thrown identity, failure phase, poison state and tick accounting. Those outputs require direct tests, not only final state equality.

Small primitive-only optimizations are not ruled out. Primitive state cannot be changed in place through a reference, so a narrowly specified primitive fast path might avoid some fingerprint work. It would still need correct setter/delete/restore bookkeeping and fingerprint-equivalence details such as JSON's handling of -0. Its usefulness depends on real state composition; the reported costly fog-memory/visibility values are composite. Do not present a primitive optimization as solving composite state costs without measurement.

Discriminating default-preserving experiment. First add contract checks for empty/nonempty stores, strict and semantic equal writes, removal/reinsert, destroyed/recycled entities, no listeners followed by getDiff, recorder/history/client/render/debug/observer consumption, live-reference mutation before/during/after a tick, listener-to-listener live mutations, and baseline/diff/listener failure phases. Preserve existing world-state tests for set/removal/unchanged-state diffs (tests/world-state.test.ts:58-93) and supported JSON getter/error tests. An actual mutation that suppresses a nonempty component payload must fail the intended full-diff assertion; a passing allocation benchmark alone is insufficient.

Then compare unchanged A/A and interleaved baseline/candidate runs on worlds with many registered but clean stores, sparse writes, and dense writes. Include representative real game state and zero/one/multiple diff consumers, including a recorder. Capture complete diffs, state snapshots/digests, events, command/execution results and non-timing structural metrics at matched boundaries. Report CPU/wall-time distributions, allocation/GC evidence and post-GC retained heap/peak RSS separately. Detailed timing fields are expected to differ; semantic counters and failure classifications are not. Reject an observed win that comes from omitted work. Count the avoided clean-store containers directly, and report any dense-write regression. A small/noisy result is an allowed outcome and does not justify unrelated changes.

Explicit-policy alternatives if larger E20 savings are desired. A setter-observed slot policy could let callers promise that every meaningful change is published through setState; in-place mutation of such a slot would intentionally stop being observed. An owned immutable-value policy could instead clone/validate and control ownership at insertion, potentially changing identity, aliasing, getters, clone failures and serialization cost. A bare Object.isFrozen check is not sufficient. Both need concrete API, inheritance/default, restore/applySnapshot/deserialize, recorder/replay and lifecycle contracts before implementation. If policy selection must survive a save, that is a persistent-format decision requiring owner approval; silently restoring a different policy is not acceptable.

An explicitly disabled-diff mode is another possible policy, not an automatic optimization. It must define getDiff availability, observer/recorder connection refusal or enablement, metrics, failure validation and restoration. No-consumer discovery based solely on listeners cannot deliver that policy safely. The default must continue to honor current consumers. None of these alternatives is approved by this investigation, and the failure of the listed shortcuts is not evidence that all default-preserving optimization is impossible.

### Codex native Astra/xhigh — E11, E13 and E15

The concrete opportunities are narrower than replacing the existing readers or runner. Keep the ordinary-JSON reader and the game-owned playtest loop while considering a bounded temporary FileSink spool experiment. The generic runner is not currently an equivalent replacement. E11/E13/E15 consumer acceptance remains open.

E11/E13 producer capability is present in the installed package. All five FileSink record iterators delegate to the fixed-block JSONL reader. dist/session-jsonl-reader.js:23-75 opens lazily, captures the file's byte horizon on first advancement, yields valid preceding records before a completed-line parse error, tolerates only the physical final unterminated malformed line, and closes its descriptor in finally. Its working memory follows the largest line plus a65,536-byte block. The horizon excludes later appends; it is not an atomic protection against rewrites/truncation. This is source confirmation of the shipped mechanism, not consumer performance or memory acceptance.

The game uses a different persistent artifact layout. scripts/playtest.mjs:46-55 publishes an ordinary .json bundle and .envelope.json. src/game/playtest/bundleIo.ts:54 writes top-level values/array elements separately, and readBundleFile at line124 parses separate pieces into one result object containing full arrays. This avoids one document-sized JavaScript string, but still materializes the bundle. The largest array element or non-array top-level value must still be materialized and parsed; describing this as constant memory or unlimited per-record size would be false.

FileSink expects manifest.json, separate ticks/commands/executions/failures/markers JSONL files, snapshot files and optional attachments (installed dist/session-file-sink.js:8-16). It cannot directly replace readBundleFile for the existing game files. Existing call sites include scripts/replay-inspect.mjs:35, run-oracles.mjs:24, playtest-findings.mjs:225, playtest-self-improve-lib.mjs:89 and playtest-corpus.mjs:126. Findings annotation also writes the ordinary JSON representation back. Converting an already materialized JSON bundle into FileSink would add work without avoiding its initial memory cost.

Work156 correctly loads one bundle, observes original metadata before progression's legacy repair, and passes that same object to progression (scripts/playtest-corpus.mjs:121-172). Fixed metric counters and O(number of runs) report rows do not make bundle loading or replay streaming. Its accepted bounded memory proof is a separate retained result; it is not repeated or expanded here into a full-corpus/FileSink/MCP claim.

Remaining whole-bundle boundaries are explicit. FileSink.toBundle collects each stream and snapshot into arrays (dist/session-file-sink.js:381-412). SessionReplayer.fromSource immediately calls source.toBundle (dist/session-replayer.js:82-83), so that factory does not provide streaming replay. BundleCorpus's loadBundle and openViewer also call FileSink.toBundle (dist/bundle-corpus.js:170-174). The inspected MCP CorpusState loads bundles and can retain four BundleViewers (mcp/src/state.ts:11-47); summary, hotspot and marker tools materialize bundles, and diff tools can load two (mcp/src/server.ts:96,109,116,241). A bounded JSONL iterator does not imply constant process memory for those compositions.

Browser paths are separate from the Node CLI. RecordingService re-embeds sidecars and JSON.stringify's the complete rewritten bundle before creating a Blob (src/game/recording/RecordingService.ts:423-443). Replay upload reads file.text and then parses complete JSON (src/ui/replay/replayLoadDialog.ts:203-215; src/game/replay/parseSessionBundleFile.ts:58-63). The Playwright LLM exporter has its own piecewise browser-to-host path (scripts/playtest-llm-host.mjs:17-31). FileSink is Node-only, and the browser-entry tests deliberately exclude it. CLI acceptance cannot stand in for browser export/import memory acceptance.

Existing oversized bundleIo tests are meaningful string-limit controls, but not a real-game memory result. tests/playtest/bundleIo.test.ts:122-158 writes an actual document beyond the V8 string ceiling and verifies eager JSON.stringify/readFileSync fail while the piecewise pair works. The fixture repeats a large shared string, so its input heap shape is intentionally unlike a long recording. Preserve that distinction.

Beneficial scoped adoption to investigate: a Node-only temporary FileSink spool for deterministic recording, retaining the existing SessionRecorder, bridge loop, returned bundle and final ordinary-JSON output. It can move historical entries out of heap during recording and exercise the shipped incremental reader during readback without publishing a new archive layout. It still incurs final toBundle materialization and synchronous disk I/O. Therefore only recording-phase memory reduction is a plausible hypothesis; no lower final peak RSS, speedup or full-run success follows without measurement.

The bounded spool experiment should compare MemorySink and FileSink on two actual game-recorded lengths, not synthetic arrays. Compare every semantic stream, initial/periodic/terminal snapshots, metadata horizons, commands and execution results, then raw replay/self-check and unchanged oracle/progression output. Normalize only documented session identity/time fields. Measure recording-phase heap, final materialization peak, total CPU/wall time and disk bytes separately, with interleaved unchanged controls. Inspect descriptor/resource closure and remove only task-owned spool artifacts after required bytes are detached. Do not retain a SessionBundle[] across samples.

Failure/lifecycle requirements precede production adoption. Exercise fresh-directory creation, initialization failure, mid-record write failure, terminal snapshot/close failure, readback failure and cleanup. Preserve original diagnostic failures when cleanup also fails. Do not return sidecar descriptors after deleting their backing storage; the current deterministic runner exposes no attachment operations, but this scope must be explicit. FileSink's fresh-directory rule and own-artifact cleanup must not affect existing recording directories or user data.

Current runPlaytest has a lifecycle boundary that must not be overstated: it connects the recorder before its try, checks lastError only inside the loop, disconnects in finally, and does not recheck lastError afterward (src/game/playtest/runPlaytest.ts:31,39-84). SessionRecorder can set lastError during terminal snapshot or close (installed dist/session-recorder.js:121-133,180-185). Additional disk failures make these boundaries practically relevant. Define and test game-side reporting for them before claiming equivalent or improved error envelopes; this report does not silently repair or reinterpret the existing behavior. Such a bounded game decision is distinct from reopening the exhausted producer budget.

Publishing FileSink directories, changing artifact discovery or migrating consumers to BundleCorpus is a persistent-format/adoption proposal requiring a concrete owner decision. A temporary compatibility experiment does not itself change the delivered format, but its execution needs the owner's resource slot and its production result needs acceptance. Browser export improvements or true streaming analysis are separate possible projects, not proof that the current Node reader is unusable.

E15 bridge advancement fits the new callback on the ordinary path. createSimulationBridge.step at src/game/simulation/createSimulationBridge.ts:296-343 flushes out-of-band rendering, reports pause/halt/match-over refusals, accumulates time, drains human intentions before AI intentions, and then steps the world. A synchronous callback using bridge.step(100) can preserve that normal one-tick boundary. Calling bare world.step would bypass the intention drain. The installed advance helper enforces exactly one tick and rejects asynchronous callbacks; it does not cancel already scheduled asynchronous work. No broader promise is inferred from the shipped helper, and no work73 repair is authorized.

Several differences are adaptable without declaring generic adoption impossible. A game adapter can derive elapsed ticks from world.tick, capture match outcome, inspect HUD halt details and supply an explicit synthetic policySeed to avoid the generic runner's otherwise additional world.random() draw (dist/synthetic-playtest.js:67-83). Those changes still need behavioral comparisons. The ordinary unit and CLI tests are not proof of complete match behavior.

The diagnostic mismatch is concrete. AoE2's loop distinguishes SinkWriteError from another recorder error, preserves errorCode/message/structured details, probes recorder error before engine halt and match outcome, and reports ticksRun as world.tick minus startTick (src/game/playtest/runPlaytest.ts:43-87). runSynthPlaytest maps every mid-run recorder.lastError to sinkError and returns no recorder error object (dist/synthetic-playtest.js:163-187; its public result type has no such field). runAgentPlaytest also uses sinkError and returns name/message/stack in agentError, omitting structured code/details (dist/ai-playtester.js:117-123,252-260). A sink wrapper can capture its own failures but cannot recover every error caught by the recorder before a sink write. Attaching a second recorder conflicts with the single-recorder contract; reading private internals is not a clean public adaptation.

Both generic runners increment ticksRun only after a tick with no recorder error, whereas the game counts elapsed world ticks, including a consumed failing tick. Generic terminal failures can change ok without changing an already chosen stopReason. The synthetic runner also intentionally permits some poisoned/policyError results with ok true, while the agent runner's ok is stricter. These are documented engine semantics, not defects authorized for repair here. Mapping them into the game oracle envelope requires preserving, rather than discarding, meaning.

Initial/terminal lifecycle behavior also differs. Generic runners inspect a connect-time lastError and propagate the original error after best-effort disconnect; the game currently detects recorder errors only after stepping inside its loop. Both generic runners own their SessionRecorder and disconnect in their own finally path. Merely replacing the while loop cannot preserve every error boundary. TerminalSnapshot is true in the generic runners and also the recorder's current default, so this is not itself a terminal-snapshot incompatibility; the diagnostic handling around finalization is the relevant distinction.

Replay must retain played-state and command ownership. The current createReplayWorldOnly factory rejects experimental save-only human-order shadows and builds the replay-safe world (src/game/simulation/replay/createReplayWorldOnly.ts:15-31). ReplayController intentionally uses different registration for replay-safe AI/pending-command handling, with selfCheck as the divergence backstop (src/game/replay/ReplayController.ts:392-399). Adding the live bridge callback indiscriminately could generate/drain commands in addition to replaying recorded submissions. Save-only human intentions, actual recorded submissions, and replay bootstrap are distinct boundaries.

The browser LLM runner has additional game requirements: paused browser-host advancement in decision-sized batches, dispatch feedback, screenshots/checkpoints, provider/cost outcomes and winner-oracle handling (src/game/playtest/llmRunner.ts:35-82,198-282; maintained llmRunner provider/oracle tests). An engine agent deciding once per tick is not a direct replacement for that orchestration. These facts justify keeping the custom runner unless a concrete adapter preserves those requirements; they do not prove that every possible future adapter is impossible.

Smallest useful E15 next step: add a game-side compatibility test of the shipped synchronous advance callback using actual bridge-generated commands and recorded/replayed state, while retaining the production loop. Cover normal advancement, match completion, consumed-tick engine failure, submission/execution order, raw replay/self-check and absence of duplicate commands. A no-op engine policy with an explicit seed can isolate wrapper advancement from new agent behavior. This establishes partial consumer compatibility only; it cannot close the explicit production adoption/error-attribution ask.

Full generic-runner replacement currently needs either an owner-approved change to the game's diagnostic contract or a separately authorized producer surface that exposes sufficient recorder diagnostics and lifecycle outcomes. Neither follows from this investigation. Work73 is exhausted5/5, and even a potentially useful additional producer feature must be proposed explicitly rather than counted as a hidden repair attempt.
